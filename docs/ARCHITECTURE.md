### 1.2 Findings (ordered by importance)
1. **Leave and Trips API is absent from the public API repository.** The web repo (`3102394 COPS Enhancement - Leave Module`)
   has `MyLeavePage`, `TeamLeavePage`, `LeaveSetupPage`, `Trips*Page` calling `/leave/*` and `/trips/*`, but the API
   has no leave/trip model, migration, route or controller (the only trace is the `LeaveLookup` interface and
   `NullLeaveLookup`). Either it was never pushed or the repositories diverged. `Lasabro.Leave` and `Lasabro.Trips`
   cannot be extracted without that source. **Needed from you.**
2. **A real database dump is committed in the public API repo**: `cops-before-compliance-repair.sql` (UTF-16, 38 tables with data,
   8 password hashes, 8 e-mail addresses, sessions, cases, chat, audit logs). Rotate credentials and purge history
   (`SECURITY-REMEDIATION.md` in bundle 00). The monorepo assembly will not import it.
3. **"All tests passed" is not true of the pushed web repository**: 2 of 128 Vitest tests failed (menu icons
   `IconConfetti`, `IconShoppingCart` seeded by Events and Procurement but never registered) and `npm run build:check`
   failed: first-load JavaScript 449.6 KB gzipped against the 400 KB budget in guide rule 2.4.8 / 8. Both fixed and
   measured in bundle 00 (128/128; 324.7 KB).
4. **Test database differs from production**: `phpunit.xml` runs on SQLite in memory while production is MySQL 8.4.
   Migrations split across plugins (below) must therefore also be verified on MySQL; the fingerprint tool does that.
5. **Authorization is route-level only.** There is no `app/Policies` folder; `Gate`/`authorize` appear 4 times.
   Everything relies on `perm:` middleware plus Eloquent global scopes. That is sound but it is not the "policies per
   plugin" you asked for; policies will be introduced per plugin **replicating existing checks exactly**, not changing them.
6. **Two-factor authentication exists for the client portal only.** Guide 8.6 requires it for staff (payroll, finance,
   directors) before HR/payroll go-live. Not part of the refactor; tracked as a Core plugin item.
7. **Repository hygiene**: 78 stray files (68 translation `.snippet` files, 4 `snippets/*.txt`, `*.php.bak`, the SQL dump, an empty
   `*.wiki` folder); 174 history comments in PHP ("Phase 4a", "Bundle 7", "added by Bundle 2") and 10 files named
   `bundleNN.ts` / `patchNN.ts` in `src/i18n` (organised by delivery date, not by feature); route files named by
   bundle; `icons.ts` has imports in the middle of the file and one `Object.assign` per bundle; `bootstrap/app.php`
   still says "compare with the skeleton generated by your Laravel version". Cleaned as each area moves into a plugin.
8. **Central registries that block modularity**: `PermissionSeeder` (all permissions), `MenuAndWidgetSeeder`,
   `routes/api.php` (29 hand-listed `require`s), `bootstrap/providers.php`, `lang/*`, `src/App.tsx` (228 lines of
   routes), `src/lib/icons.ts`, `src/i18n/index.ts`. Each becomes a per-plugin declaration (section 3).
9. **Good seams already exist and are reused**: per-domain service providers, `config('cops.approval_handlers' / approval_permissions / code_prefixes)`
   extension arrays, `LeaveLookup`/`NullLeaveLookup` (interface with a null default), lookup tables instead of enums,
   `BelongsToOrganization` tenancy trait.
10. Documentation is organised by phase (`PHASE-4A…8E`, 5 `REGRESSION-CHECKLIST-phase*.md`, 5 `openapi-phase*.yaml`);
    these merge into one document per plugin.

## 3. Target architecture

### 3.1 Repository layout
```
lasabro/
├─ brand/                         logos, icons, colour tokens (bundle 01)
├─ kit/                           the startup kit: edition-agnostic, versioned, published
│  ├─ framework/                  composer lasabro/framework  - plugin engine, contracts, support traits, CLI
│  ├─ contracts/                  OpenAPI base, manifest JSON Schema, theme-token schema (language-neutral)
│  ├─ web-core/                   npm @lasabro/kit      - TypeScript, NO UI framework: registry, manifest client, permissions, theme, i18n
│  ├─ web-react/                  npm @lasabro/kit-react - Mantine shell, layouts, slots, DataList, RichTextField…
│  └─ starter/                    template for `lasabro edition:new <name>` (also `composer create-project`)
├─ plugins/
│  └─ hr/                         one folder per plugin (anatomy below)
├─ editions/
│  └─ enterprise/
│     ├─ api/                     thin Laravel app: composer.json lists the plugins, config, .env.example
│     └─ web/                     thin Vite app: package.json lists the web plugins, generated registry
├─ docs/  .github/  baseline/
└─ composer.json, package.json    workspace roots
```

### 3.2 Anatomy of a plugin
```
plugins/hr/
├─ composer.json                  name lasabro/hr; `extra.lasabro` = manifest (single source of truth)
├─ src/
│  ├─ HrServiceProvider.php       routes, policies, commands, schedule, contracts
│  ├─ Http/{Controllers,Requests,Resources}
│  ├─ Models/  Services/  Policies/  Observers/  Console/  Events/  Listeners/  Jobs/
├─ routes/api.php                 every route declares permission and data scope
├─ database/{migrations,seeders}  reversible migrations, idempotent seeders
├─ resources/
│  ├─ permissions.php  menu.php  widgets.php  lookups.php   declarations, synced idempotently on activation
│  └─ lang/{en,fr,rw,sw}/        server texts, namespaced `lasabro-hr::…`
├─ tests/{Unit,Feature}           travel with the plugin
├─ web/react/                     npm @lasabro/hr-react: pages, components, i18n slices, icons, `plugin.ts`
│  (web/vue/, web/angular/, flutter/ may be added later next to it)
└─ docs/                          README (generated dependency notice), CHANGELOG, API reference
```

### 3.3 The manifest (`extra.lasabro` in `composer.json`)
```json
"extra": { "lasabro": {
  "id": "Lasabro.Hr", "title": "Human Resources", "tier": "domain",
  "provider": "Lasabro\\Hr\\HrServiceProvider",
  "requires": { "Lasabro.Core": "^1.0", "Lasabro.Approvals": "^1.0" },
  "suggests": { "Lasabro.Leave": "adds leave balances to attendance absence detection" },
  "frontends": { "react": "@lasabro/hr-react" },
  "declares": ["permissions", "menu", "widgets", "lookups"]
}}
```
(The no-JSON rule of the guide concerns database columns; a manifest file is configuration, like `composer.json` itself.)

### 3.4 Lifecycle and the dependency notice (requirements 3, 4, 10)
* **install** = Composer package present + migrations run + declarations synced; **activate / deactivate** toggle at runtime;
  **uninstall** removes the package; data are dropped only with an explicit `--purge` and never while a dependent is active.
* State lives in new tables only: `lasabro_plugins` (id, code, version, is_active, installed_at, activated_at),
  `lasabro_plugin_resources` (which permission/menu/widget/lookup codes a plugin owns), `lasabro_plugin_events` (history).
  Existing tables are not altered, which is what keeps the fingerprint identical.
* A compiled cache `bootstrap/cache/lasabro.php` (like `config:cache`) lists active providers, so boot never queries the database.
* `requires` (hard) blocks activation with a plain message: *"Lasabro.Payroll requires Lasabro.Hr ^1.0, Lasabro.Attendance ^1.0 and
  Lasabro.Rules ^1.0. Missing: Lasabro.Attendance (installed but inactive)."* and blocks deactivating a plugin others need.
  The same sentence appears in the Plugin Manager UI, in `lasabro plugin:info`, and in each plugin's generated README.
* `suggests` (soft) is integration through contracts: the existing `LeaveLookup` / `NullLeaveLookup` pattern generalised, so
  Attendance works alone and gains leave awareness when `Lasabro.Leave` is active.
* Deactivation unloads routes, commands, schedule and policies, hides owned menu items and widgets, and the web shell
  stops mounting the plugin's screens; no data is touched.

### 3.5 Permissions, menu, widgets, lookups
Each plugin declares its own in `resources/*.php`; activation upserts them by code (the current `updateOrCreate` logic), replacing
the central seeders. Permission codes stay character-for-character identical (`hr.leave.request`…), so roles keep working.
Role matrix management stays in Core; plugins only contribute permissions and default role grants.

### 3.6 Frontend: dynamic and framework-agnostic (requirement 11)
Contract between any client and the API: **OpenAPI + `GET /api/v1/kit/manifest`** (edition, enabled plugins and versions, menu
tree for the user, permissions, widgets, theme tokens, locales). Nothing in it is React-specific.
* `@lasabro/kit` (TypeScript, no UI framework): plugin registry, manifest client, permission helpers, theme-token engine, i18n loader.
* `@lasabro/kit-react`: Mantine implementation (shell, layouts, DataList, RichTextField, SafeHtml…) = today's `src/components`.
* Each plugin's web package calls `definePlugin({ id, routes, icons, widgets, slots, i18n })` with lazy imports, so a plugin that is
  deactivated, or never visited, costs zero first-load bytes (the 400 KB budget is enforced per edition).
* Angular/Vue/Flutter: add `kit-vue`/`kit-angular`/a Dart package that speak the same manifest, plus `plugins/*/web/vue` etc.
  Nothing in the API or the plugin engine changes.
* Installing a web plugin = `npm install`, then `lasabro web:sync` regenerates `plugins.generated.ts` (static imports are what
  Vite needs for code-splitting); activation at runtime is driven by the manifest.

### 3.7 Customisable layout, theme, components, widgets, partials (requirement 6)
* **Theme tokens** (colours, typography, radius, density, logo light/dark) stored as rows, served in the manifest, applied as CSS
  variables and mapped to the UI library's theme. Presets: `lasabro` (default), `cops-classic`, custom per organization.
* **Layouts** are registered components (`sidebar`, `topbar`, `compact`) chosen by setting.
* **Slots** (named extension points): `header.right`, `header.left`, `sidebar.top`, `sidebar.bottom`, `page.header`, `page.footer`,
  `dashboard.widgets`, `profile.tabs`, `login.aside`. Plugins contribute widgets/partials to slots; administrators order or hide them.
* **Widgets** keep today's model (`dashboard_widgets`, per-role arrangement) and become plugin-declared.
* The logo is theme-aware: `logo-horizontal-light.svg` on light surfaces, `logo-horizontal-dark.svg` on dark or coloured ones.

### 3.8 Package management from the kit (requirement 7)
`lasabro package:add composer|npm <name> [--dev]`, `package:remove`, `package:list`, `package:audit`, `plugin:install lasabro/<name>`.
Implemented with `Symfony\Process` (arguments as arrays, never a shell string), vendor allow-list (`lasabro/*`, `@lasabro/*`) unless
`--allow-third-party`, binaries and working directories from config, every run audited. The Plugin Manager UI can trigger them as a
queued job with a streamed log, **disabled by default in production** (`LASABRO_PACKAGE_MANAGER=cli`): a web request that can run
`composer` is an attack surface and is opt-in, requires `plugins.install`, and is rate-limited.

## 5. How "everything stays the same" is proven
1. **Fingerprint** (`lasabro:fingerprint`, bundle 00): routes with guards, permissions, role grants, menu, widgets, lookups, full schema,
   commands, schedule, registries, captured on a freshly seeded MySQL database before the first move and compared after every bundle.
2. **Existing tests move with their code and must stay green**: 20 feature + 27 unit test files on the API (about 300 test methods), 128 tests on the web.
3. **Schema adoption, not recreation.** Table names, columns and migration file names do not change. Migration files owned by one plugin
   move unchanged (same file name, so `migrations` rows still match). Mixed files (the foundation migration) are split into guarded
   migrations (`if (Schema::hasTable(...)) return;`) and the original stays as a documented no-op marker. Existing databases are
   adopted without data movement.
4. **Namespaces are free to change** (no class names persisted). The only exception is the queue: drain the queue (`php artisan queue:work --stop-when-empty`)
   before deploying, because `jobs` rows store class names.
5. **Plugin matrix in CI** (bundle 02 onward): boot the app with each plugin and only its dependencies; activate/deactivate cycles; a deactivated plugin must
   leave no route, command or menu entry.
6. Each bundle ships a README with the exact apply steps, the fingerprint result, and any intentional addition (for example the three `lasabro_*` tables).

## 7. Risks and open points
* **Leave and Trips source** (finding 1) blocks bundle 08 only; everything before it proceeds.
* API tests are unrunnable in my sandbox, so API bundles reach you with PHP syntax checked and pure logic executed, but with
  the behavioural proof coming from your machine (`php artisan test` plus the fingerprint compare). Expect a short fix round per API bundle.
* Splitting mixed migrations is the most delicate step; it is done on the foundation migration first (bundle 04) with MySQL fingerprinting.
* The Plugin Manager running `composer` from the web is a deliberate, opt-in risk (3.8).
* Payroll, leave and procurement carry the legal caveats of guide Appendix C unchanged; moving code does not change their legal status.
